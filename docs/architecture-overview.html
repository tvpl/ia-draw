Architecture Canvas é um editor de diagramas — infraestrutura cloud, C4, fluxos de negócio — construído sobre o Excalidraw. A diferença: cada traço é salvo no servidor antes de você perceber. E o motor de IA que monta o diagrama a partir de uma descrição em português, sempre com preview pra aprovar ou descartar antes de qualquer coisa grudar na tela, está entregue e verificado como API — o dock que o expõe dentro do editor é a próxima fatia de produto, não uma tela que já existe.

Mockup ilustrativo, não uma captura de tela. O painel de IA à direita desenha o fluxo que a API já implementa (proposta, diff, aprovar/descartar); nenhum componente equivalente existe hoje em apps/web.

Onde o projeto está, sem arredondar

Os 92 requisitos de F0–F5 são um contrato de backend verificado: cada um foi checado onda a onda por um Verifier independente, com evidência em arquivo:linha. É a parte forte do trabalho e ela está de pé.

A superfície de produto vem atrás e é medida à parte. Das 26 capacidades do mapa de capacidades, 4 têm tela e 22 são backend-only — API verificada, nenhum componente em apps/web que as exponha. Em rotas: das 82 rotas REST registradas, 4 são consumidas pela interface e 78 não têm consumidor (inventário).

As seções marcadas contrato de backend · sem tela abaixo descrevem capacidades dessa segunda lista. O CI roda repo-tools audit a cada pull request e falha quando o mapa declara uma superfície que não é um componente existente em apps/web. O portão cobre o mapa contra o código, não esta página contra o mapa — a correspondência entre este texto e as entradas do mapa continua sendo revisão humana.

02

Descreva. Aprove. Pronto.

contrato de backend · sem tela

Você escreve o que precisa em português. A IA monta uma proposta — nunca aplica nada sozinha. Você vê exatamente o que vai mudar antes de decidir, e um clique em Desfazer sempre volta pro estado de antes.

Esse fluxo inteiro está implementado e verificado no servidor — POST /diagrams/:id/ai/runs, a prévia, o limiar de aprovação e o snapshot pre_ai que o undo restaura — e nenhuma parte dele tem interface. Não existe dock de IA em apps/web: hoje a capacidade só é alcançável por chamada de API. Ela é a primeira fatia vertical do roadmap de produto justamente por ser o diferencial declarado.

Componentes prontos pra usar

Peça pelo nome e a IA resolve pela biblioteca do workspace, já com layout aplicado — nunca posicionado no olho:

VPC + subnets EKS event-driven three-tier web mobile + BFF API Gateway + Lambda observability stack C4 starter

Duas travas, sempre ligadas

  • O que está escrito dentro do diagrama nunca vira instrução pra IA. Um label, comentário ou metadado de um elemento é tratado como dado, nunca como comando — mesmo que alguém escreva algo tipo "ignore as regras anteriores" dentro de uma caixa do canvas, isso não tem efeito nenhum sobre o que o agente faz.
  • Mudança arriscada sempre pede aprovação explícita: remover algo, alterar mais de 50 elementos de uma vez, ou mexer fora do que você tinha selecionado. Fora isso, tudo o que a IA aplica primeiro grava um snapshot do estado anterior — desfazer é literalmente restaurar esse snapshot, não um "melhor esforço".

Exatamente onde você parou — cada lote de mutação já tinha sido confirmado pelo servidor antes de qualquer coisa aparecer como salva.

  • Snapshots automáticos e nomeáveis — comparáveis lado a lado e restauráveis como uma nova revisão, sem apagar o que veio depois.
  • Conflito estrutural nunca descarta dado. Se duas edições brigam pelo mesmo elemento, as duas variantes ficam preservadas pra comparação — nada some silenciosamente.
  • Export de emergência a qualquer momento em .excalidraw, SVG, PNG e PDF — mesmo se o servidor de IA ou a colaboração em tempo real estiverem fora do ar.

Esta é a seção com mais superfície real. A persistência server-first, a confirmação "Salvo" e a recuperação da fila local depois de um crash do navegador estão no editor hoje (DiagramEditorPage.tsx, syncClient.ts). Os três itens acima — snapshots nomeáveis, comparação de variantes em conflito e export — são backend-only: as rotas de snapshot e export existem e são testadas, o botão que as chama não.

Fala os formatos que o seu time já usa

contrato de backend · sem tela

Nada fica preso dentro do Architecture Canvas — nem o que entra, nem o que sai.

Export, import, Mermaid/Structurizr, a geração de documentação e o lint arquitetural são backend-only. Cada formato listado abaixo tem rota registrada e teste; o "botão Gerar documentação" descreve a chamada POST /diagrams/:id/specs:generate, não um botão que existe na tela.

.excalidraw PNG SVG PDF Mermaid Structurizr DSL CSV / JSON (inventário)

A geração de documentação produz um Markdown estruturado a partir do canvas — resumo, contexto, componentes, integrações, riscos, decisões — com cada seção linkada de volta ao elemento do diagrama que a originou. Campo sem metadado vira literalmente "não especificado": a IA nunca inventa uma decisão que ninguém tomou.

O lint avisa quando algo parece errado

Um lint arquitetural roda no servidor — sempre como aviso, nunca bloqueando o desenho:

Componente órfão — nada conectado a ele.
Fluxo sem direção — seta ausente ou ambígua.
Trust boundary ausente — dado sensível cruzando fronteira sem marcação.
Single point of failure — um nó sozinho carregando tudo.
Secret como texto — senha ou chave escrita direto no diagrama.
Conector sem protocolo — liga dois nós sem dizer como.
06

Pronto pra produção, não só pra demo

contrato de backend · sem tela

Cada item aqui existe porque alguém precisou dele de verdade num ambiente corporativo — não é checklist de vitrine.

Os cinco itens abaixo rodam no servidor e na infraestrutura, e são configurados por variável de ambiente, job ou provedor de identidade. Todos são backend-only: não existe tela de administração no produto — nem para provider de IA, nem para membros do workspace, nem para auditoria.

AUTENTICAÇÃO

Login corporativo (OIDC)

Conecta no provedor de identidade que o time já usa. Grupos mapeiam pra papéis com um teto explícito — ninguém sobe de nível sozinho, mesmo que o token sugira.

AUDITORIA

Toda ação fica registrada

Quem mudou o quê, quando e de onde — trilha de auditoria completa, não um log de erro que só ajuda depois que já deu problema.

BACKUP

Backup que já foi restaurado de verdade

Um job recorrente restaura a cadeia inteira contra um banco isolado e cruza checksum com contagem de linhas antes de dizer que está tudo bem — nunca confia só porque o arquivo existe.

OBSERVABILIDADE

Métricas e alertas prontos

Latência, fila de jobs, custo estimado de IA, falhas de login — um painel Prometheus/Grafana opcional já vem configurado.

LIMITES

Ninguém derruba o servidor sozinho

Rate limiting por usuário, mais rígido nas rotas de geração por IA e de export, que são as mais caras.

Comece agora

Um Makefile na raiz do repositório embrulha tanto o stack Docker completo quanto os comandos de desenvolvimento do dia a dia — rode make help a qualquer momento pra ver a lista inteira.

com Docker (stack completo)

# builda tudo, sobe o stack, roda as migrations

# http://localhost:8080 quando os health checks ficarem verdes

make logs              # acompanhar os logs
make ps                # status de cada serviço
make down               # parar — os dados continuam nos volumes

sem Docker (loop rápido de dev)

make install
make ci                 # lint + typecheck + unit + integration
make web-dev              # apps/web sozinho, Vite + HMR

Testes de integração rodam contra Postgres real via PGlite — sem precisar do Docker (ADR-0007). Perfis opcionais do Docker: make up-observability (Prometheus/Grafana/OTel) e make up-oidc (um Keycloak local pra testar login OIDC).

Como funciona por baixo dos panos — o invariante server-first

O navegador nunca é a fonte da verdade. Toda alteração de canvas — vinda de um formulário REST comum ou de uma conexão WebSocket aberta — passa por exatamente uma função de escrita no servidor antes de existir.

Reconciliação por elemento (LWW)

Em vez de um CRDT genérico sobre o documento inteiro (Yjs), cada elemento de cena carrega seu próprio version e versionNonce — o modelo nativo do Excalidraw. Em empate de version, o menor versionNonce vence. O resultado é um histórico de operações legível e auditável, sem precisar materializar o documento inteiro para inspecionar uma mudança.

Pipeline completo do agente de IA

O texto de dentro do canvas nunca vira instrução. É a regra estrutural que impede injeção de prompt — não uma promessa de que "o modelo vai se comportar".

canal de dados não-confiável (conteúdo do canvas) caminho de escrita/aprovação

Geração vs. edição

  • Criação: o modelo emite uma diagram-ir/v1 completa (nós, containers, edges semânticos) em uma única chamada — mais barato e visualmente consistente do que dezenas de chamadas de ferramenta. O servidor resolve componentes da biblioteca por stable_key e aplica layout determinístico (grid-zones, elk-layered ou swimlane conforme o tipo de diagrama) — nunca o LLM decide posição de pixel.
  • Edição incremental: tools como create_element, connect_elements ou auto_layout retornam um AbstractPatch — nunca escrevem direto no banco ou fazem chamada de rede.
Presença em tempo real — arquitetura

Cursores e seleção de outros usuários propagam via WebSocket sem nunca tocar o PostgreSQL — perder presença nunca arrisca conteúdo durável.

Backup, restore e observabilidade — arquitetura

Um backup nunca é confiável só porque foi criado. A fase de hardening (F5) adiciona um job recorrente que restaura de verdade e compara o resultado.

Observabilidade e segurança de produção

  • Métricas (GET /metrics, Prometheus) cobrem latência REST/WS, ACK de mutação (mesma série para os dois transportes), fila de jobs, tokens/custo estimado de IA, falhas de snapshot/restore/login.
  • Tracing (OpenTelemetry) encadeia spans de contexto → chamada de IA → apply — nunca com prompt, cena ou token em nenhum atributo, provado por busca de substring nos spans capturados.
  • OIDC com PKCE mapeia grupos do provedor de identidade para papéis, com teto explícito — um grupo não mapeado nunca herda um papel elevado, mesmo que o token traga claims sugestivos.
  • Rate limiting por usuário, com limites mais estritos nas rotas de geração de IA e de export — a mesma classe de limitador reaproveitada desde a fase F2.
Roadmap — as 6 fases, 92/92 requisitos de backend verificados

Cada fase foi fechada com um verificador independente antes da próxima começar — nunca a mesma sessão que escreveu o código atestando que ele está correto. O que foi verificado é o contrato de backend: das 26 capacidades entregues nessas seis fases, 22 continuam sem superfície de produto, e fechar essa distância é o roadmap seguinte.

F0

Fundação verificado

Monorepo, compose local, migrations, health checks, spikes de renderização server-side e do adaptador do Excalidraw.

F1

Persistência server-first verificado

Contas/RBAC, o op-log e a reconciliação LWW, recuperação após crash, snapshots com restore, upload de assets, export local e backup com restore testado.

F2

IA geradora verificado

Configuração segura de provider, a IR declarativa diagram-ir/v1, layout determinístico, biblioteca de componentes e o agente com prévia/aprovação/undo. O MVP interno mínimo do roadmap termina aqui.

F3

Documentação e visão completa verificado

Geração de spec a partir do canvas, apresentações navegáveis, lint arquitetural/C4, import-export Mermaid/Structurizr, comentários assíncronos.

F4

Colaboração em tempo real verificado

Primeiro transporte novo do projeto (WebSocket) e primeira dependência externa opcional (Redis) — ambos provados com engines reais. Links de compartilhamento e webhooks assinados.

F5

Hardening de produção verificado

OIDC com PKCE, rate limiting, auditoria completa, backup incremental + teste de restore automatizado, métricas Prometheus, tracing OpenTelemetry, acessibilidade. Fecha o roadmap.

ADR-0001

Op-log LWW nativo do Excalidraw, não Yjs/CRDT — auditoria e diff legíveis de graça.

ADR-0002

Roadmap AI-first — geração por IA entregue antes da colaboração multiplayer.

ADR-0003

Monólito modular — um processo Node, fronteiras nos packages, split futuro trivial.

ADR-0004

IR declarativa como peça central da geração e do architecture-as-code.

ADR-0005

Render server-side via SVG + rasterização, sem Chromium obrigatório.

ADR-0006

Sem Redis no MVP — pg-boss sobre PostgreSQL; Redis só entra para presença.

ADR-0007

PGlite para testes de integração de Postgres sem Docker.

ADR-0008

Zero import por valor do Excalidraw em código server-side.

ADR-0009

PresenceBroadcaster injetável — memória por padrão, Redis quando configurado.
