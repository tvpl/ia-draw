Diagramas que o servidor
é dono de verdade.

Architecture Canvas é uma plataforma self-hosted de diagramação técnica sobre o Excalidraw. Todo desenho — infraestrutura cloud, C4, fluxos de negócio — vive persistido no PostgreSQL a cada alteração, nunca só no navegador. Um agente de IA gera e edita esses diagramas a partir de linguagem natural, sempre com prévia, aprovação explícita e undo real.

FOLHA 01

O invariante server-first

O navegador nunca é a fonte da verdade. Toda alteração de canvas — vinda de um formulário REST comum ou de uma conexão WebSocket aberta — passa por exatamente uma função de escrita no servidor antes de existir.

Reconciliação por elemento (LWW)

Em vez de um CRDT genérico sobre o documento inteiro (Yjs), cada elemento de cena carrega seu próprio version e versionNonce — o modelo nativo do Excalidraw. Em empate de version, o menor versionNonce vence. O resultado é um histórico de operações legível e auditável, sem precisar materializar o documento inteiro para inspecionar uma mudança.

FOLHA 02

Como o roadmap foi entregue

Seis fases, cada uma fechada com um verificador independente antes da próxima começar — nunca a mesma sessão que escreveu o código atestando que ele está correto.

F0

Fundação verificado

Monorepo, compose local, migrations, health checks, spikes de renderização server-side e do adaptador do Excalidraw.

F1

Persistência server-first verificado

Contas/RBAC, o op-log e a reconciliação LWW, recuperação após crash, snapshots com restore, upload de assets, export local e backup com restore testado.

F2

IA geradora verificado

Configuração segura de provider, a IR declarativa diagram-ir/v1, layout determinístico, biblioteca de componentes e o agente com prévia/aprovação/undo. O MVP interno mínimo do roadmap termina aqui.

F3

Documentação e visão completa verificado

Geração de spec a partir do canvas, apresentações navegáveis, lint arquitetural/C4, import-export Mermaid/Structurizr, comentários assíncronos.

F4

Colaboração em tempo real verificado

Primeiro transporte novo do projeto (WebSocket) e primeira dependência externa opcional (Redis) — ambos provados com engines reais. Links de compartilhamento e webhooks assinados.

F5

Hardening de produção verificado

OIDC com PKCE, rate limiting, auditoria completa, backup incremental + teste de restore automatizado, métricas Prometheus, tracing OpenTelemetry, acessibilidade. Fecha o roadmap.

FOLHA 03

O agente de IA

O texto de dentro do canvas nunca vira instrução. É a regra estrutural que impede injeção de prompt — não uma promessa de que “o modelo vai se comportar”.

canal de dados não-confiável (conteúdo do canvas) caminho de escrita/aprovação

Geração vs. edição

  • Criação: o modelo emite uma diagram-ir/v1 completa (nós, containers, edges semânticos) em uma única chamada — mais barato e visualmente consistente do que dezenas de chamadas de ferramenta. O servidor resolve componentes da biblioteca por stable_key e aplica layout determinístico (grid-zones, elk-layered ou swimlane conforme o tipo de diagrama) — nunca o LLM decide posição de pixel.
  • Edição incremental: tools como create_element, connect_elements ou auto_layout retornam um AbstractPatch — nunca escrevem direto no banco ou fazem chamada de rede.
FOLHA 04

Presença em tempo real

Cursores e seleção de outros usuários propagam via WebSocket sem nunca tocar o PostgreSQL — perder presença nunca arrisca conteúdo durável.

FOLHA 05

Backup, restore e observabilidade

Um backup nunca é confiável só porque foi criado. A fase de hardening (F5) adiciona um job recorrente que restaura de verdade e compara o resultado.

Observabilidade e segurança de produção

  • Métricas (GET /metrics, Prometheus) cobrem latência REST/WS, ACK de mutação (mesma série para os dois transportes), fila de jobs, tokens/custo estimado de IA, falhas de snapshot/restore/login.
  • Tracing (OpenTelemetry) encadeia spans de contexto → chamada de IA → apply — nunca com prompt, cena ou token em nenhum atributo, provado por busca de substring nos spans capturados.
  • OIDC com PKCE mapeia grupos do provedor de identidade para papéis, com teto explícito — um grupo não mapeado nunca herda um papel elevado, mesmo que o token traga claims sugestivos.
  • Rate limiting por usuário, com limites mais estritos nas rotas de geração de IA e de export — a mesma classe de limitador reaproveitada desde a fase F2.

FOLHA 07

Decisões que moldaram o sistema

Texto completo de cada uma em docs/adr/.

ADR-0001

Op-log LWW nativo do Excalidraw, não Yjs/CRDT — auditoria e diff legíveis de graça.

ADR-0002

Roadmap AI-first — geração por IA entregue antes da colaboração multiplayer.

ADR-0003

Monólito modular — um processo Node, fronteiras nos packages, split futuro trivial.

ADR-0004

IR declarativa como peça central da geração e do architecture-as-code.

ADR-0005

Render server-side via SVG + rasterização, sem Chromium obrigatório.

ADR-0006

Sem Redis no MVP — pg-boss sobre PostgreSQL; Redis só entra para presença.

ADR-0007

PGlite para testes de integração de Postgres sem Docker.

ADR-0008

Zero import por valor do Excalidraw em código server-side.

ADR-0009

PresenceBroadcaster injetável — memória por padrão, Redis quando configurado.
